# IntentLane: system search/open implementation research

Research date: 23 September 2026. This note is the implementation reference
for the macOS 27 content-app pilot and the generated mapping template. It is
not proof that NetNewsWire has this integration today. Apple Developer
documentation, WWDC sessions, Apple's sample projects, and the installed
Xcode 27 SDK are the sources of authority.

## Correction to the initial pilot wording

The current macOS 27 SDK deprecates `.system.search` at 27.0 and explicitly
directs adopters to `.system.searchInApp`. The primary search/open pair for a
new macOS 27 implementation is therefore **`.system.searchInApp` and
`.system.open`**, not the old `.system.search` spelling. The public
[System and in-app search](https://developer.apple.com/documentation/appintents/app-schema-domain-system-and-in-app-search)
domain page is the product reference; the installed SDK is the exact source
for the symbol spelling and availability.

This was verified in
`MacOSX27.0.sdk/.../AppIntents.swiftinterface`: `SystemIntent.search` has
`deprecated: 27.0, message: "Use .system.searchInApp instead"`, while
`searchInApp` and `open` are available on `anyAppleOS 27.0`. The generator
must compile an adoption against the customer's installed target SDK rather
than hard-coding a stale spelling.

Apple's separately published API references for
[the old search schema](https://developer.apple.com/documentation/appintents/assistantschemas/systemintent/search)
and [the open schema](https://developer.apple.com/documentation/appintents/appschema/systemintent/open)
remain useful to understand the generated shape: the search action implements
in-app search criteria and the open action receives a resolved target. The SDK
deprecation wins for a new 27-target implementation.

## What Apple requires for a real content integration

Apple describes the Siri AI path as a combination, not a single intent:

1. Model the app's useful content as an `AppEntity`.
2. Make searchable content an `IndexedEntity` and donate it to Core
   Spotlight.
3. Adopt the system schemas that truthfully represent the app's action.
4. Make the entity query recover an entity from the app's source of truth.
5. Test business logic, query and Spotlight behaviour with
   `AppIntentsTesting`; then check Spotlight and perform a manual Siri AI
   journey.

Apple says that schemas are the contract the system uses to identify, query
and understand app content/actions, and that indexing lets semantic Spotlight
search make content available to Siri AI. See
[Apple Intelligence and Siri AI](https://developer.apple.com/documentation/appintents/apple-intelligence-and-siri-ai),
[App schema domains](https://developer.apple.com/documentation/appintents/app-schema-domains),
and [Build intelligent Siri experiences with App Schemas (WWDC26)](https://developer.apple.com/videos/play/wwdc2026/240/).

`AppIntent` or `AppShortcutsProvider` alone is consequently not evidence of
Siri AI discovery. Shortcuts may be tested as a separate, explicitly requested
automation surface, but it is not part of this default integration or its
acceptance criteria.

## Generated layer versus application-owned mapping

IntentLane should generate deterministic declarations and an adapter protocol;
the client application supplies only its app-specific data access and UI
navigation. Apple recommends a standalone entity structure for most models,
rather than attaching `AppEntity` to a heavyweight persistent model. That is
the right boundary for a generator: the generated entity is a small, safe
projection of an application record.

Source: [Defining app entities for your custom data types](https://developer.apple.com/documentation/appintents/defining-app-entities-for-your-custom-data-types).

| Generated by IntentLane | Filled by the application owner |
| --- | --- |
| `ArticleEntity` declaration, schema annotations, localized display metadata and indexed property declarations | Mapping an actual record to `ArticleEntity`, including a stable ID |
| `ArticleEntityQuery` skeleton and `IndexedEntityQuery` reindexing hooks | Exact-ID retrieval, text search, full corpus retrieval and no-match behaviour |
| `.system.searchInApp` / `.system.open` declaration shapes derived from the target SDK | Search screen routing and opening the selected article in the existing UI |
| `ArticleIndexingService` lifecycle skeleton | Calling it after a committed feed refresh, update, deletion, account removal or full reindex request |
| XCTest / AppIntentsTesting test skeleton | Fixture store, app dependency injection and assertions tied to its real navigation |

### Mapping contract that should be generated

The template should require the following operations and keep it free of
NetNewsWire classes:

```swift
protocol ArticleIntentLaneAdapter: Sendable {
    func entity(for stableID: String) async throws -> ArticleEntity?
    func entities(matching text: String) async throws -> [ArticleEntity]
    func allIndexableEntities() async throws -> [ArticleEntity]
    @MainActor func showSearchResults(for text: String) async throws
    @MainActor func openArticle(stableID: String) async throws
}
```

The app adapter must return `nil` for an unknown stable ID and an empty array
for a title with no valid match. It must never substitute a different article
as a fallback. For the pilot fixture, Alpha, Beta and Gamma must have distinct
stable IDs; a request for an invented title produces no entity and opens
nothing.

The final generated API names and exact schema members must come from the
installed SDK's Xcode macro Fix-Its. Apple specifically demonstrates that
Xcode can generate a schema adoption with required declarations and stub
implementation; the developer then injects dependencies, processes input and
opens the app's existing UI. [WWDC26 App Schemas](https://developer.apple.com/videos/play/wwdc2026/240/)

## Entity and Spotlight lifecycle

The generated entity should conform to `IndexedEntity`, contain only data the
product has approved for system search, and expose indexed properties through
Apple's property wrappers. `IndexedEntity` has default implementations, while
`@ComputedProperty(indexingKey:)` can map an entity property to a standard
Spotlight key and `customIndexingKey` can add an app-defined key.

Source and working Apple pattern:
[Making app entities available in Spotlight](https://developer.apple.com/documentation/appintents/making-app-entities-available-in-spotlight).

The index lifecycle must be application-owned and driven by completed data
changes, never just app launch:

| App event | Adapter/indexer action |
| --- | --- |
| Initial install, account enabled, or successful feed refresh | Map changed/new records and call `CSSearchableIndex(name: …).indexAppEntities(_)`. |
| Article metadata changes | Re-index the mapped entity with the same stable ID. |
| Article/feed/account removed or made non-searchable | Call `deleteAppEntities(identifiedBy:ofType:)` for exact IDs. |
| System requests recovery | `IndexedEntityQuery.reindexEntities` refetches IDs and donates them; `reindexAllEntities` does the same for the approved corpus. |

Apple's direct donation example is a named `CSSearchableIndex` followed by
`indexAppEntities`. Apple also requires `IndexedEntityQuery` when entities are
donated this way, so Spotlight can request a subset or complete reindex.
Sources: [Making app entities available in Spotlight](https://developer.apple.com/documentation/appintents/making-app-entities-available-in-spotlight),
[IndexedEntityQuery](https://developer.apple.com/documentation/appintents/indexedentityquery), and
[deleteAppEntities(identifiedBy:ofType:)](https://developer.apple.com/documentation/corespotlight/cssearchableindex/deleteappentities%28identifiedby%3Aoftype%3A%29).

For a large initial or account-wide refresh, batch the work with Core
Spotlight's `beginBatch()` / `endBatch()` rather than treating every entity as
an independent sync. The named-index policy, update/delete lifecycle and batch
behaviour are covered by [Adding your app’s content to Spotlight indexes](https://developer.apple.com/documentation/corespotlight/adding-your-app-s-content-to-spotlight-indexes).

The Apple **Travel Tracking** sample, linked from the
[App Intents updates page](https://developer.apple.com/documentation/updates?changes=__2),
is the canonical example to inspect for an app-owned store, entity projection,
direct donation and reindexing. It is a pattern, not a model to copy: an RSS
client must index only articles the user expects to be searchable, respect
account/feed removal, and avoid sending private article text or credentials
into Spotlight without product approval.

## Tests and acceptance sequence

`AppIntentsTesting` is the automated contract layer. Apple describes it as a
test framework that exercises intents through the same infrastructure as Siri,
Shortcuts and Spotlight without UI automation. The CometCal sample in Apple's
[Validate your App Intents adoption with AppIntentsTesting (WWDC26)](https://developer.apple.com/videos/play/wwdc2026/295/)
shows this progression:

1. Load the installed app's intent definitions and invoke an intent with
   fixture parameters.
2. Query the entity definition with text and assert the exact returned entity.
3. Test Spotlight indexing through the framework.
4. Use a normal `XCUIApplication` assertion only where opening a view needs
   visual confirmation.

The generated test template should require these cases:

| Test | Required assertion |
| --- | --- |
| Exact resolution | Alpha returns Alpha's stable ID; Gamma returns Gamma's stable ID. |
| Negative resolution | An invented title returns zero entities. |
| Search action | The adapter receives the exact query and routes to in-app search. |
| Open action | Opening Alpha calls the existing app router with Alpha's stable ID. |
| Index lifecycle | Insert/update/delete and full/subset reindex delegate to the expected store records. |
| Surface proof | Spotlight finds the intended fixture; a human tests Siri AI after automated tests pass. |

Apple's own recommended order is: AppIntentsTesting, then Spotlight (and
Shortcuts only when it is a claimed surface), then a complete Siri experience.
The last step is manual because an automated contract test proves the
integration path, not a particular natural-language result under every OS,
locale or account condition. Record OS build, Xcode build, locale, region,
fixture feed and outcome for that test. Source:
[Build intelligent Siri experiences with App Schemas (WWDC26)](https://developer.apple.com/videos/play/wwdc2026/240/).

## Implementation decisions for IntentLane

1. Introduce a **primary Siri AI content package**, distinct from all
   Shortcuts generation, with target-SDK-derived `.system.searchInApp` and
   `.system.open` support.
2. Emit an adapter protocol, a compile-failing default implementation or clear
   TODO methods, an `IndexedEntityQuery` skeleton and a lifecycle service.
   Do not pretend the generator knows a customer's persistence or navigation
   model.
3. Add contract fields for stable ID source, privacy-approved indexed fields,
   supported locales and navigation handoff, and reject a package with no
   mapping implementation in a real target.
4. Add AppIntentsTesting fixtures for positive, negative, collision and
   reindex cases. Keep manual Siri evidence in the ledger, not in code
   generation claims.
5. Document `searchInApp` as the macOS 27 spelling. Keep any compatibility
   use of the older `.system.search` isolated behind an SDK availability rule,
   with a deprecation warning treated as a generator defect for a new 27
   target.
